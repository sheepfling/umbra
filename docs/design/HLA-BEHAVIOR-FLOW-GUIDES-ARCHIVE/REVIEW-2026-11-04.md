## 2025 configured-process Disconnect/reconnect callback lifecycle — 2026-11-04

Disconnect first commits the local not-joined-to-not-connected transition and
resets the shared dispatcher under the ambassador lock. For the process
profile, it then interrupts the client before scheduler shutdown, closes the
adapter CallbackSession outside the lock (preventing new old-session entry and
waiting for active invocation), and calls client close. Client close joins its
workers, clears pending events and joined identity, then closes the bridge;
bridge close cancels projections, closes the process session, and resets the
shared dispatcher again. Thus a sequential Connect after Disconnect returns
starts after old callback cleanup has finished.

After process ConnectionLost, the client remains owned by the ambassador. A
later Connect replaces it during commit; the old client's destructor calls
close, so its session and bridge cleanup finish before Connect returns.
Concurrent Connect and Disconnect are different: the local state becomes Not
Connected before Disconnect finishes its post-lock cleanup. Since the old
bridge resets the same dispatcher used by the replacement session, that late
reset could discard newly queued work. This is source-derived possibility;
the pinned API concurrency contract and runtime outcome are unverified.

Focused public process evidence covers an empty-queue Connect/Disconnect only;
the same-ambassador Disconnect/reconnect case is embedded-profile evidence.
No configured-process queue or concurrent lifecycle test was found. Corrected
the callback evidence table and Disconnect flow ordering. The updated Mermaid
flow rendered with Mermaid CLI 12.0.0 and passed local screenshot review.
Inventory remains 31 guides / 391 diagrams; selected visual QA is 124 reviewed
/ 0 pending. No source, tests, builds, CI, Requirements Lab, or 2010 content
changed.
