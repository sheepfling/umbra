## 2025 configured-process Disconnect/reconnect callback lifecycle — 2026-11-04

Successful process Disconnect resets the shared dispatcher under the lifecycle
lock, interrupts the client socket, closes the adapter callback session and
waits for active invocation, then joins client workers, clears buffered client
events, and closes the bridge. Bridge close cancels pre-callback projections,
closes its session, and resets the same dispatcher again. A sequential Connect
after Disconnect returns starts after old cleanup completes. ConnectionLost
differs: it retains the old client, which a later Connect destroys during
commit; the client's destructor calls close before Connect returns.

Disconnect publishes Not Connected before its post-lock cleanup completes. A
concurrent Connect can commit a replacement before the old bridge resets the
shared dispatcher, so old cleanup could clear tasks queued for the replacement
session. This is a source-derived race possibility only; neither the pinned API
concurrency contract nor focused test behavior has been established. The
configured-process public case covers one Connect/Disconnect with an empty
callback queue, while the same-ambassador Disconnect/reconnect case is
embedded-only. Repaired the callback guide's malformed evidence-table row and
